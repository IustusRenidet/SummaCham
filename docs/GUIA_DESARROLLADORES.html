Guía completa para futuros desarrolladores

Esta guía documenta la implementación actual de SummaCham a nivel de archivos, flujo funcional y puntos de extensión. Fue escrita para que cualquier desarrollador nuevo pueda entender rápidamente que toca cada capa.

Electron + Express SQLite local + Firebird externo Frontend en HTML/JS Actualizada: 2026-02-13

1) Objetivo y alcance

El sistema es una app de escritorio con Electron que levanta un servidor Node/Express local y sirve un frontend de planeación financiera. La app sincroniza información de presupuestos/reportes desde Firebird y guarda estado operativo, usuarios, layouts y sesiones en SQLite.

Entradas principales del runtime

  • main.js: proceso principal de Electron (ventana, tray, updates, arranque backend).
  • src/server.js: API Express + sesiones + rutas + estáticos.
  • vistas/app.html: shell del frontend (React + iframe para módulos).
Ejemplo en lenguaje natural: imagina un restaurante. main.js es el local abierto al público, server.js es la cocina donde se preparan las órdenes, y app.html es el menú que ve el cliente.

2) Inicio rápido para desarrollo

Requisitos

  • Node.js 18+.
  • Windows (flujo principal de este repo).
  • Firebird disponible si se quieren datos reales.

Comandos de arranque

npm install
npm run native:ensure
npm start          # Electron + backend

# Alternativa: backend sin Electron
npm run server

Variables relevantes

  • NODE_ENV, SERVER_PORT, SESSION_SECRET.
  • PANELAMCHAM_JWT_SECRET, PANELAMCHAM_REFRESH_SECRET.
  • PANELAMCHAM_ADMIN_PASSWORD para usuario ICONET.
  • FIREBIRD_HOST, FIREBIRD_PORT, FIREBIRD_USER, FIREBIRD_PASSWORD.
Qué es una variable de entorno: es un dato de configuración que el sistema lee al iniciar, sin escribirlo fijo en el código.
Ejemplo simple: SERVER_PORT=3005 significa "arranca el servidor en el puerto 3005".
Qué es un secreto: es una clave privada que solo el sistema debe conocer para firmar tokens o proteger sesiones.
Ejemplo simple: SESSION_SECRET funciona como la firma de seguridad de las galletas de sesión.
Ejemplo en lenguaje natural: si una variable de entorno fuera una etiqueta en una caja, diría: "usar esta puerta", "usar este usuario", "usar este password". El programa lee esas etiquetas al arrancar.
Nota: en entorno Electron los secretos se autogeneran por src/utils/secretsManager.js en .env.secrets bajo el data dir.

3) Conceptos desde cero (si no sabes programar)

Esta sección traduce el proyecto a lenguaje simple. Si esta es tu primera vez viendo código, aquí está el mapa mental mínimo para no perderte.

Diccionario rápido

  • Frontend: lo que ve el usuario (pantallas en vistas/*.html).
  • Backend: lógica en servidor (archivos en src/routes y src/services).
  • API / endpoint: URL que el frontend llama para pedir o guardar datos, por ejemplo /api/auth/login.
  • Request: la petición que envía el frontend al backend.
  • Response: la respuesta que regresa el backend (JSON, error, etc).
  • JSON: formato de datos (llaves/valores), por ejemplo { "usuario": "ICONET" }.
  • Sesión: estado de usuario logueado para no pedir password cada click.
  • Token JWT: credencial firmada para autenticar requests.
  • Base de datos: donde se guardan datos. Aquí hay dos: SQLite (local) y Firebird (contable externo).

Conceptos técnicos adicionales (con ejemplo sencillo)

Middleware: paso intermedio que revisa una petición antes de llegar a la lógica final.
Ejemplo: un guardia en la entrada que valida si traes credencial.
CORS: regla que define desde qué origen (sitio/app) se permite llamar la API.
Ejemplo: lista de invitados permitidos para entrar a una fiesta.
Cookie: pequeño dato que el navegador guarda para recordar sesión.
Ejemplo: un sello en la mano para no volver a mostrar boleto.
Hash: versión irreconocible de una contraseña.
Ejemplo: en vez de guardar la llave original, guardas su molde.
Ruta API: dirección específica de una acción del backend.
Ejemplo: /api/auth/login = "ventanilla para iniciar sesión".
Payload: contenido útil que viaja dentro del request o response.
Ejemplo: en login, el payload de entrada lleva usuario y contrasena.
Status HTTP: código de resultado de una petición.
Ejemplos: 200 (ok), 400 (dato inválido), 401 (no autenticado), 500 (error interno).
Método HTTP: tipo de acción sobre la API.
Ejemplos: GET (leer), POST (crear/enviar), PUT/PATCH (actualizar), DELETE (eliminar).
Script: comando automatizado para ejecutar una tarea repetitiva.
Ejemplo: npm test corre pruebas sin hacerlo manualmente una por una.
Build: proceso de empaquetar la app para distribuirla.
Ejemplo: convertir ingredientes sueltos en un producto final instalable.

Ejemplo real: qué pasa cuando haces login

  1. Usuario escribe usuario/password en vistas/login.html.
  2. Frontend hace POST /api/auth/login.
  3. src/routes/auth.js valida datos, busca usuario en SQLite y compara password.
  4. Si todo bien, backend crea sesión y tokens JWT.
  5. Frontend guarda sesión en localStorage vía vistas/js/sesion.js.
  6. Al abrir módulos, el frontend manda headers de autenticación automáticamente.
  7. Si el token expira o no hay sesión, redirige a login.html.
Resumen simple: "escribo usuario y password, el sistema revisa, me da permiso temporal y me deja entrar a las pantallas que me corresponden".

Express (servidor HTTP)

Crea la API y define rutas.

// Importa la libreria Express para crear servidor web
const express = require("express");
// Crea la aplicacion principal de Express
const app = express();

// Define una ruta GET en /api/salud
app.get("/api/salud", (req, res) => {
  // Devuelve JSON al cliente con estado "ok"
  res.json({ estado: "ok" });
}); // Cierra definicion de ruta

Ejemplo natural: Express es la recepción que decide a qué ventanilla va cada solicitud.

Joi (validación de datos de entrada)

Se usa para validar req.body o req.query antes de procesar. Evita errores y ataques por datos malformados. 

// Importa Joi para validar datos
const Joi = require("joi");

// Define esquema esperado para login
const esquemaLogin = Joi.object({
  // usuario debe ser texto, quitar espacios, minimo 2 caracteres y obligatorio
  usuario: Joi.string().trim().min(2).required(),
  // contrasena debe ser texto de minimo 6 caracteres y obligatoria
  contrasena: Joi.string().min(6).required()
});

// Valida el body recibido (si no existe, usa objeto vacio)
const { error, value } = esquemaLogin.validate(req.body || {}, { abortEarly: false });
// Si hay error de validacion, corta flujo y regresa 400
if (error) {
  return res.status(400).json({ mensaje: "Datos invalidos" });
} // Si no hay error, "value" trae datos ya validados

Ejemplo natural: Joi es un formulario con reglas: si falta un campo obligatorio, no te deja continuar.

Helmet (headers de seguridad)

Agrega headers HTTP seguros para reducir vectores comunes de ataque. En este proyecto se usa así: 

// Importa Helmet (headers de seguridad HTTP)
const helmet = require("helmet");
// Activa Helmet en todas las rutas del servidor
app.use(helmet({ contentSecurityPolicy: false })); // CSP se deja desactivado por compatibilidad

contentSecurityPolicy: false se desactiva por compatibilidad con vistas actuales. Si se endurece seguridad, este punto debe revisarse primero.

Ejemplo natural: Helmet es como poner cerraduras extra a puertas y ventanas del servidor.

express-session + better-sqlite3-session-store

Mantiene sesiones de usuario en SQLite para soportar múltiples usuarios concurrentes. 

// Importa middleware de sesion
const session = require("express-session");
// Crea store de sesion en SQLite
const SqliteStore = require("better-sqlite3-session-store")(session);

// Registra middleware de sesion
app.use(session({
  // Guarda sesiones en SQLite usando conexion actual
  store: new SqliteStore({ client: getDb() }),
  // Firma criptografica de cookie de sesion
  secret: process.env.SESSION_SECRET,
  // Nombre de cookie que viaja al navegador
  name: "panelamcham.sid",
  // No reescribir sesion si no hubo cambios
  resave: false,
  // No crear sesion vacia para usuarios anonimos
  saveUninitialized: false
})); // A partir de aqui req.session esta disponible

Ejemplo natural: la sesión es un gafete temporal para que no te pidan login en cada acción.

bcryptjs (hash de contrasenas)

No se guarda password en texto plano, se guarda hash.

// Importa bcrypt para hash de contrasenas
const bcrypt = require("bcryptjs");

// Convierte contrasena nueva en hash seguro (12 rondas)
const hash = bcrypt.hashSync(nuevaContrasena, 12);
// Compara texto ingresado vs hash almacenado en base de datos
const coincide = await bcrypt.compare(contrasenaActual, hashGuardado);

Ejemplo natural: bcrypt guarda una huella, no la contraseña real.

jsonwebtoken (JWT)

Firma y valida tokens de acceso/refresco.

// Importa libreria JWT
const jwt = require("jsonwebtoken");

// Firma token con "sub" (subject = id usuario), usando secreto y expiracion 1h
const tokenAcceso = jwt.sign({ sub: usuarioId }, JWT_SECRET, { expiresIn: "1h" });
// Verifica token recibido usando el mismo secreto de firma
const payload = jwt.verify(tokenAcceso, JWT_SECRET);

Ejemplo natural: JWT es un pase firmado: si la firma no coincide, el pase es inválido.

better-sqlite3 (BD local rapida)

Driver SQLite sincrono, usado para usuarios, permisos, layouts, bitacora, etc.

// Importa driver SQLite
const Database = require("better-sqlite3");
// Abre (o crea) archivo de base local
const db = new Database("datos/panel.sqlite");
// Activa modo WAL para concurrencia de lectura/escritura
db.pragma("journal_mode = WAL");
// Si hay lock, espera hasta 5000 ms antes de fallar
db.pragma("busy_timeout = 5000");

Ejemplo natural: SQLite aquí funciona como una libreta local ordenada del sistema.

node-firebird (conexión a contabilidad Firebird)

Consulta tablas contables por empresa/año.

// Abre conexion con Firebird usando opciones (host, puerto, usuario, password, database)
Firebird.attach(opciones, (errorConexion, conexion) => {
  // Si no conecta, termina con error
  if (errorConexion) return reject(errorConexion);
  // Ejecuta query SQL con parametros
  conexion.query(sql, params, (error, rows) => {
    // Cierra conexion siempre para no dejar recursos abiertos
    conexion.detach();
    // Si la consulta falla, devuelve error
    if (error) return reject(error);
    // Si todo sale bien, devuelve filas
    resolve(rows);
  });
});

Ejemplo natural: abrir conexión, pedir datos, cerrar conexión; igual que entrar a un archivo fisico y volver a guardarlo.

electron-updater + auto-launch

electron-updater busca actualizaciones; auto-launch configura arranque automático de la app en el sistema.

Ejemplo natural: uno revisa si hay versión nueva; el otro hace que la app arranque sola al encender la PC.

7.1 Origen y transformación de Request/Response (explicado paso a paso)

Request: datos que el cliente envía al servidor.
Response: datos que el servidor devuelve al cliente.
Transformación: cambios que hace el backend entre entrada y salida (validar, normalizar, enriquecer, filtrar permisos, etc.).

Diagrama general de request/response

[Frontend]
   |
   | 1) request (URL + metodo + headers + body)
   v
[Router Express]
   |
   | 2) valida (Joi) + auth/permisos + normaliza datos
   v
[Servicio de negocio]
   |
   | 3) consulta/combina datos (SQLite/Firebird)
   v
[Router Express]
   |
   | 4) arma response (status + JSON)
   v
[Frontend]
   |
   | 5) pinta tabla, grafica, mensaje o error

Ejemplo A: Login (POST /api/auth/login)

Origen del request: formulario de vistas/login.html.

// 1) Cliente envia credenciales al backend
fetch("/api/auth/login", {
  method: "POST", // Metodo HTTP para crear una sesion
  headers: { "Content-Type": "application/json" }, // Formato enviado
  body: JSON.stringify({
    usuario: "ICONET", // Dato capturado en UI
    contrasena: "******" // Dato capturado en UI
  })
});

Transformación en backend: validación + consulta + armado de sesión.

// 2) Router valida estructura con Joi
const { error, value } = esquemaLogin.validate(req.body || {}, { abortEarly: false });
if (error) return res.status(400).json({ mensaje: "Verifica los datos capturados." });

// 3) Normaliza usuario para busqueda consistente
const usuarioBuscado = value.usuario.trim().toUpperCase();

// 4) Busca usuario en SQLite y compara hash de contrasena
const registro = db.prepare("SELECT * FROM usuarios WHERE usuario = ?").get(usuarioBuscado);
const contrasenaCorrecta = await bcrypt.compare(value.contrasena, registro.contrasena);

// 5) Si valida, construye objeto de sesion y emite JWT
const sesion = await construirSesion(registro);
const tokens = emitirTokens({ id: registro.id, usuario: registro.usuario });

Response final al cliente: objeto enriquecido con permisos y tokens.

{
  "usuario": {
    "id": 1,
    "usuario": "ICONET",
    "permisosPorEmpresa": { "...": "..." }
  },
  "empresaActiva": { "id": "empresa1", "nombre": "Ciudad de México" },
  "tokenAcceso": "eyJ...",
  "tokenRefresco": "eyJ..."
}
Traducción simple: entran 2 campos (usuario/password), salen datos completos de sesión para que la app sepa quien eres y que puedes hacer.

Ejemplo B: Reporte (GET /api/reportes/resumen)

Origen del request: vista de reporte en frontend.

// Cliente pide reporte por empresa y anio

{

  "anio": 2026,
  "detalle": [ ... ],

Traducción simple: frontend pide "dame resumen 2026", backend junta varias fuentes, calcula y devuelve un resultado ya ordenado para mostrar.

2) Conexión SQLite: crearConexion() en src/db/sqlite.js

// Crea y configura conexion SQLite
const crearConexion = () => {
  // Calcula ruta final del archivo panel.sqlite
  const rutaDb = path.join(obtenerRutaBaseDatos(), "panel.sqlite");
  // Abre archivo de base de datos
  const db = new Database(rutaDb);
  // Activa integridad referencial (llaves foraneas)
  db.pragma("foreign_keys = ON");
  // Activa WAL para mejorar concurrencia
  db.pragma("journal_mode = WAL");
  // Espera 5s cuando la base esta temporalmente bloqueada
  db.pragma("busy_timeout = 5000");
  // Devuelve conexion lista para usar
  return db;
};

Esta configuración permite mejor concurrencia cuando hay múltiples usuarios activos.

Ejemplo natural: varios usuarios pueden trabajar sin bloquearse tanto entre si.

3) Conexión Firebird: ejecutarConsulta() en src/services/firebirdService.js

// Ejecuta consulta Firebird para empresa especifica
const ejecutarConsulta = (empresaId, consulta, parametros = []) => {
  // Devuelve Promise para manejar flujo asincrono
  return new Promise((resolve, reject) => {
    // Construye opciones de conexion (host, puerto, db path, user, pass)
    const opciones = crearOpciones(empresaId);
    // Intenta conectar a Firebird
    Firebird.attach(opciones, (err, con) => {
      // Si no conecta, rechaza Promise
      if (err) return reject(err);
      // Ejecuta SQL con parametros
      con.query(consulta, parametros, (errorConsulta, rows) => {
        // Cierra conexion inmediatamente despues de la consulta
        con.detach();
        // Si la consulta falla, rechaza
        if (errorConsulta) return reject(errorConsulta);
        // Si va bien, entrega filas resultantes
        resolve(rows);
      });
    });
  });
};

Este patron (attach -> query -> detach) evita dejar conexiones abiertas.

Ejemplo natural: cómo usar una sala de juntas: entrar, hacer reunión, salir y cerrar.

17.5 Exportar Excel con gráfica nativa (backend + PowerShell + Excel COM)

Aquí se genera un archivo que incluye objetos de gráfica nativos de Excel. Se usa en endpoints como: /api/reportes/operativo-excel-native y /api/reportes/resumen-excel-native.

Flujo request/response de esta exportación

  1. Frontend crea un libro base (tabla + hoja de datos de gráficas).
  2. Frontend envía ese libro en binario (application/octet-stream) al backend.
  3. Backend guarda temporalmente el archivo y ejecuta script PowerShell.
  4. PowerShell abre Excel vía COM, crea chart objects y guarda salida.
  5. Backend devuelve el nuevo .xlsx como descarga HTTP.
// Estructura de hoja de datos para chart nativo (patron CHART)

["CDMX", 1200, 1100, 1000]
["GDL", 800, 760, 700]
["MTY", 650, 620, 590]

[]

return { buffer: bufferSalida, filename };
# POWERSHELL: crea chart objects reales en Excel
$excel = New-Object -ComObject Excel.Application
# Abre workbook que envio el backend como input
$wb = $excel.Workbooks.Open($inputFull)
# Toma hoja de datos (ej. OperativoData o GraficasData)
$wsData = $wb.Worksheets.Item($DataSheetName)
# Crea objeto grafica en hoja destino
$chart = $wsCharts.ChartObjects().Add(20, $chartTop, 1120, 420)
# Asigna rango de datos del que se alimenta la grafica
$chart.Chart.SetSourceData($rangeValues)
# Guarda archivo final con charts nativos
$wb.SaveAs($OutputPath)
Esta ruta requiere entorno Windows con Excel instalado (usa Excel.Application vía COM).
Ejemplo en lenguaje natural: el frontend manda "materia prima" (xlsx base), backend manda a un "operador Excel real" (PowerShell+COM), y regresa el archivo ya armado.

17.6 Cómo exportar en el día a día

  1. Desde Graficas.html: usa botón Excel para exportar reporte visual con imágenes de gráficas.

  3. Desde RESUMEN: usa exportación que manda GraficasData a /api/reportes/resumen-excel-native y devuelve xlsx con charts Excel.
